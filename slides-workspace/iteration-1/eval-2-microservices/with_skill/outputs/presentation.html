The Problem

Why We Need
To Move

Our Django monolith has served us well, but growth has exposed structural limits that slow delivery and increase risk.

1
Deployment Bottleneck
Every change requires a full monolith deploy. A single broken test blocks all teams. Average deploy cycle has grown to 4+ hours.
2
Scaling Limitations
Search and analytics workloads consume resources that starve billing and auth. We can only scale everything together, wasting compute.
3
Team Coupling
Six teams share one codebase. Merge conflicts, unclear ownership, and implicit dependencies create friction and slow feature delivery.
4
Technology Lock-in
The monolith constrains us to a single Python/Django stack. Some domains (search, analytics) would benefit from purpose-built technology.

04 / 08

Phase 1 — Months 1-3

Foundation &
Auth Service

Establish the infrastructure backbone and extract Auth as the first service. Auth has the clearest boundaries and is a prerequisite for all other services.

1
Deploy API Gateway
Set up the API gateway with routing rules that initially proxy all traffic to the monolith. This allows incremental migration with instant rollback.
2
Build CI/CD Pipeline
Create a shared pipeline template for containerized services. Includes automated testing, canary deployments, and observability integration.
3
Extract Auth Service
Migrate user authentication, session management, and JWT issuance. Run in shadow mode alongside the monolith to validate correctness before cutover.
4
Set Up Event Bus
Deploy the asynchronous messaging infrastructure. Define the initial event schema contracts that services will use for cross-domain communication.
05 / 08

Phases 2 & 3 — Months 4-12

Core Extraction
& Completion

Phase 2 tackles the revenue-critical services in parallel. Phase 3 extracts the remaining domains and decommissions the monolith.

P2
Billing Service (Months 4-6)
  • Migrate subscription and payment logic with Stripe integration
  • Dual-write to both systems during transition window
  • Validate revenue reconciliation before monolith cutover
P2
Content & Search (Months 5-8)
  • Extract core domain models into the Content service
  • Build Search on Elasticsearch with real-time indexing via events
  • Strangler fig pattern: route reads to new service, then writes
P3
Notifications & Analytics (Months 9-12)
  • Decouple notification dispatch into event-driven service
  • Move analytics to ClickHouse for high-throughput event ingestion
  • Decommission monolith once all traffic is routed to services

Risk Assessment

Key Risks &
Mitigations

Every migration carries risk. We have identified the highest-impact threats and mapped concrete mitigations for each.

High Data Consistency During Dual-Write
Running two systems in parallel creates a window where data can diverge. Payment data is especially sensitive to inconsistency.
Reconciliation Jobs Idempotent Writes Billing
High Distributed System Complexity
Network failures, partial outages, and cascading timeouts are new failure modes the team has not operated at scale before.
Circuit Breakers Retry Policies Observability
Medium Team Skill Gap
Teams are experienced with Django but less so with container orchestration, event-driven patterns, and distributed tracing.
Training Program Platform Team Support
Medium Feature Velocity Dip
Migration work competes with product roadmap. Risk of stakeholder pressure to pause migration if feature delivery slows visibly.
Dedicated Migration Squad Parallel Tracks
