01

Current State

Understanding the monolith we are leaving behind

The Django Monolith Today

A single deployable containing all business domains

django-monolith
Auth
Billing
Notifications
Search
Content
Analytics

Single PostgreSQL database · Shared ORM models · Celery task queue

Pain Points

  • Deployment risk — every change deploys everything
  • Scaling bottleneck — cannot scale search independently of billing
  • Team coupling — 4 squads stepping on each other in one repo
  • Long CI cycles — full test suite takes 38 min
  • Tech lock-in — everything must be Python/Django

Why Migrate Now?

Business and technical drivers forcing the decision

Scale

10x Traffic Growth

Projected traffic over the next 18 months requires independent scaling of search and content delivery.

Velocity

Team Autonomy

Squads need to deploy independently without cross-team coordination for every release.

Reliability

Blast Radius

A billing bug should not take down search. Fault isolation is a top-level SRE requirement.

Decision Criteria

The migration was approved after evaluating three options: (1) continue with the monolith, (2) modular monolith, and (3) full microservices. Option 3 was selected because it best satisfies our scaling, autonomy, and fault-isolation requirements, despite higher upfront complexity.

The Six Services

Bounded contexts and responsibilities

🔒

Auth Service

User identity, registration, login, OAuth, JWT issuance, role-based access control. Owns the users and roles tables.

💳

Billing Service

Subscriptions, invoices, payment processing (Stripe integration), usage metering. Owns subscriptions, invoices.

🔔

Notifications Service

Email, push, in-app notifications. Template management, delivery tracking, preference center.

🔍

Search Service

Full-text and faceted search backed by Elasticsearch. Indexing pipeline, query parsing, relevance tuning.

📄

Content Service

CRUD for articles, media, tags, categories. Versioning, drafts, publishing workflow. Core domain.

📊

Analytics Service

Event ingestion, aggregation, dashboards. Writes to ClickHouse, exposes pre-computed metrics via API.

Data Strategy

Database-per-service with event-driven synchronization

Principle

Database per Service

Each service owns its data store. No direct cross-service database access. This enforces loose coupling and allows each team to choose the best storage engine.

Sync Pattern

Event-Driven (Outbox Pattern)

Services publish domain events via the transactional outbox pattern. Consumers build local read-optimized projections (CQRS).

Consistency

Eventual Consistency

Cross-service queries are eventually consistent. Sagas handle distributed transactions (e.g., billing + notifications on subscription change).

03

Migration Phases

A four-phase incremental approach using the Strangler Fig pattern

Phase Overview

Incremental extraction using the Strangler Fig pattern

Phase 1 — Weeks 1-6

Foundation & Auth Extraction

Set up infrastructure (API Gateway, CI/CD pipelines, observability). Extract the Auth service first — it has the fewest inbound dependencies and every other service needs it.

Phase 2 — Weeks 7-14

Extract Notifications & Search

Notifications is event-driven and largely decoupled. Search is read-heavy with a clear Elasticsearch boundary. Both can be extracted in parallel by separate squads.

Phase 3 — Weeks 15-24

Extract Billing & Content

These are the core domain services with deep coupling. Billing requires careful handling of Stripe webhooks and subscription state. Content has the largest data footprint.

Phase 4 — Weeks 25-30

Extract Analytics & Decommission Monolith

Migrate analytics event pipeline to ClickHouse. Remove legacy code paths. Decommission the monolith database. Run bake-in period.

Phase 1: Foundation & Auth Extraction

Weeks 1–6 — Laying the groundwork

Infrastructure

Platform Setup

  • Kubernetes cluster provisioning
  • API Gateway (Kong / Envoy) deployment
  • CI/CD pipeline templates per service
  • Centralized logging (ELK) and tracing (Jaeger)
  • Service mesh basics (mTLS, retries)
Auth Service

First Extraction

  • Extract user model, registration, login endpoints
  • JWT token issuance moved to standalone service
  • Monolith becomes a consumer of Auth API
  • Dual-write period: monolith + Auth DB in sync
  • Feature flag to toggle between old and new auth

Exit Criteria

Auth service handling 100% of authentication traffic. Monolith no longer writes to auth tables. Latency p99 within 10% of monolith baseline. Zero auth-related incidents for 7 consecutive days.

Phase 2: Notifications & Search

Weeks 7–14 — Parallel extraction of two decoupled domains

Notifications

Event-Driven by Nature

  • Already consumes events from Celery — switch to Kafka consumer
  • Extract email/push templates and delivery logic
  • Implement preference service endpoint
  • Migrate Celery notification tasks to dedicated workers
Search

Clear Data Boundary

  • Already backed by Elasticsearch — extract indexing pipeline
  • New gRPC API for query execution
  • Content change events trigger re-indexing via Kafka
  • Monolith search views proxy to new service

Exit Criteria

All notifications routed through the new service. Search latency p50 under 80ms. Monolith no longer directly queries Elasticsearch. Both services independently deployable and monitored.

Phase 3: Billing & Content

Weeks 15–24 — The hardest phase: core domain extraction

Billing

High-Stakes Domain

  • Migrate Stripe webhook handlers to billing service
  • Implement saga for subscription lifecycle events
  • Shadow-mode billing: run old + new in parallel, compare outputs
  • PCI compliance review for the new service boundary
  • Data migration for invoices and payment history
Content

Largest Data Footprint

  • Extract article CRUD, media uploads (S3), tagging
  • Implement content versioning in the new service
  • Migrate publishing workflow and draft states
  • Zero-downtime PostgreSQL data migration (pglogical)
  • CDN integration for media serving

Exit Criteria

Billing shadow mode shows zero discrepancies for 14 days. Content service handles full CRUD load. All Stripe webhooks processed by billing service. No direct ORM access to billing/content tables from monolith.

Phase 4: Analytics & Decommission

Weeks 25–30 — Final extraction and monolith retirement

Analytics

Event Pipeline Migration

  • Move event ingestion from Django middleware to Kafka consumers
  • Migrate from PostgreSQL aggregation queries to ClickHouse
  • Build pre-computed dashboard metrics API
  • Backfill historical data into ClickHouse
Decommission

Monolith Retirement

  • Remove all legacy code paths behind feature flags
  • Shut down monolith Celery workers
  • Decommission shared PostgreSQL database
  • Archive monolith repository
  • 2-week bake-in monitoring period

Exit Criteria

Monolith receives zero traffic. All services green on SLOs for 14 days. Shared database connections at zero. Post-mortem and lessons learned documented.

Key Risks

What could go wrong, and how we plan to handle it

Risk Matrix

Top risks ranked by impact and likelihood

# Risk Likelihood Impact Mitigation
R1 Data inconsistency during dual-write High High Transactional outbox pattern; reconciliation jobs; shadow-mode comparison
R2 Increased latency from network hops Medium High Service mesh with connection pooling; gRPC for internal calls; aggressive caching
R3 Billing data loss during migration Medium Critical Shadow billing mode; dual-write with reconciliation; rollback plan with <5 min RTO
R4 Team skill gaps in distributed systems Medium Medium Training program; embedded SRE on each squad; architecture decision records (ADRs)
R5 Scope creep / migration fatigue High Medium Strict phase gates; no new features during extraction; weekly migration standups
R6 Observability gaps in new architecture Medium Medium Mandatory distributed tracing; SLO dashboards per service before go-live

Risk Deep Dive

Detailed mitigation strategies for the top three risks

R1 — Data Inconsistency

Dual-Write Hazard

  • Use the transactional outbox — never write to two databases in one operation
  • Nightly reconciliation jobs compare old and new data stores
  • Feature flags enable instant rollback to monolith code path
  • Alerts fire if reconciliation diff exceeds threshold
R3 — Billing Data Loss

Financial Data Safety

  • Shadow mode: new service processes in parallel but does not commit
  • Output comparison: automated diff of old vs. new invoice calculations
  • 14-day shadow period before cutover
  • Rollback plan tested in staging with <5 min RTO
R5 — Scope Creep

Migration Fatigue

  • Strict phase gate reviews — no phase starts until prior phase exits
  • Feature freeze on migrating domains during extraction
  • Dedicated migration squad; not shared with feature work
  • Weekly standup focused solely on migration progress
